# E-EXAM Stage 2B.1 — terminal notification reconciliation (#225)

Status: **DRAFT / NOT READY / NOT DEPLOYED** (25 October 2026). Scope: the E-EXAM V2 runtime for all CBTA Functions 7.1–7.10; no source, item, approval or regulatory state changes.

## Confirmed failure and recovery boundary

PR #319 / issue #40 ensure a truthful, once-only committed terminal transition for candidate and expiry-sweep paths. However, the post-commit `notifySubmissionEvents()` and `notifyResultAvailableForAttempt()` work may be interrupted before `notification_log` receives an outbox row. The normal sweep only finds `in_progress` attempts. A terminal attempt with no event intent is otherwise invisible to outbox retries.

The draft `lib/email/reconcile-terminal.ts` uses **authoritative committed** terminal attempt + result state to look for **absent logical email idempotency keys**, then invokes the existing tenant-aware notification orchestrators. It never performs an email network call within a SQLite exam transaction. The outbox `idempotency_key UNIQUE` prevents duplicate logical rows. A persistent bounded cursor and **frozen per-pass high-water attempt ID** prevent continuous new submissions from indefinitely starving old failed pre-outbox events. Each pass scans only IDs at or below its persisted ceiling; on exhaustion it restarts from the beginning with a fresh ceiling. A changed deliberate UTC cutover resets the cursor/ceiling. This is bounded *scanning*, not proof of outbox provider delivery or fair scheduling under concurrent cron workers. The same sweep endpoint already authenticated with `SWEEP_TOKEN` performs this check **after** its ordinary expiry sweep.

### What is eligible

- `EXAM_SUBMITTED` candidate confirmation: only when an eligible terminal attempt has a candidate email and the expected `exam-submitted/<candidateId>/<submittedAt>` key is absent.
- `EXAM_SUBMITTED_ADMIN`: current configured administrator alert address and/or current group's educational manager when email exists; recipient keys are derived by the existing orchestration. **Historical manager/recipient changes must be reviewed before any retroactive backfill.**
- `RESULT_AVAILABLE`: only where a real `results.grading_state='COMPLETE'` exists, a candidate email exists, and the configured `result_email_policy` is not `NO_EMAIL`. Never send a partial result for `AWAITING_MANUAL_REVIEW`.
- No recovery of orphan terminal attempts with **no** `results` record; those require the separate controlled #37 historical reconciliation.

### Known unresolved delivery gap — do not close #225 yet

The existing provider retry worker `processOutboxRetries()` only selects `notification_log.status='FAILED'`. A crash after inserting an outbox row **but before sending** can strand a `QUEUED` row; a crash after setting `SENDING` can strand a `SENDING` row. The new missing-key reconciler deliberately treats those rows as *present*, not candidates for a second logical event. This avoids accidental duplicate email creation but **does not** guarantee delivery. A separately reviewed and tested recovery strategy must handle these states, including ambiguous provider outcomes, Resend idempotency limitations, correct historical sender identity, bounded retries and alerting; do not naively resend potentially delivered messages.

The frozen-snapshot fairness regression creates continuously arriving synthetic Function 7.2 attempts and verifies recovery of an earlier failed event while newer ones continue to progress. Its new exact-head CI result must be confirmed independently before changing readiness status. Migration of the reconciliation scan state on initial opt-in or a changed cutover can revisit old *missing* logical keys; select the timestamp and recipients deliberately before production enablement.
